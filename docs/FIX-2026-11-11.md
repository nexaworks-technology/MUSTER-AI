## 1. Meetings

**Root cause.** The spec (§5) lists "Meetings & QBRs" as a top-level screen. In `src/config/features.ts` it was `href: null`, and a `features.test.ts` comment recorded that as deliberate ("remain href: null in top-level nav"). So no `/meetings` index route existed, the nav never showed it, and the sidebar (`NAV_GROUPS` in `src/app/(app)/layout.tsx`) would have dropped it anyway because it was in no group. `/meetings/qbr/new` and `/meetings/qbr/[id]` worked because they are separate pages added in M10/M12. Per CLAUDE.md the spec wins over the code; the decision is recorded here.

**Not reproduced: "link on some screens, missing on others".** The sidebar is one shared layout for every `(app)` route and the link never existed in code, so there was no per-screen variation to find. A likely source is Today's own "Meetings (n)" section heading. After the fix, an e2e visits 18 screens (Today, Home, Accounts, Account 360 and its Health tab, Health, Tasks, Approvals, Renewals, Expansion, Plays, Inbox, Promises, Reports, Ask AI, Meetings, New QBR, Settings) and asserts the link is present on each. On a phone-width screen the sidebar is a horizontal strip; the new specs are desktop-only like the other flow specs, so that layout was not re-checked here.

**Fix.**
- `src/modules/meetings/list.ts`: `listMeetingsIndex` (re-exported from `service.ts`, as the module-boundary lint rule requires). Upcoming and past meetings plus QBRs, limited to the member's book (`bookWhere` on `accounts:view`; same rule as Accounts). A meeting no account was matched to is shown only to members whose scope is the whole workspace. Cancelled meetings are left out. Optional `accountId` filter.
- `/meetings` page (list of meetings and QBRs, a "Generate a QBR" button to `/meetings/qbr/new` for members who can edit accounts) and an Account 360 **Meetings** tab (`/accounts/[id]/meetings`).
- Nav: `Meetings & QBRs` now has `href: "/meetings"`, milestone **12**, `SHIPPED_MILESTONE = 12`, added to the sidebar's Work group with an icon. It is milestone 12, not 10, so the existing rule "a later milestone adds a row and never edits an existing one" holds: rows 1–11 in `features.test.ts` are untouched, and a new row 12 was added.
- `e2e/m1-foundation.spec.ts`: one entry ("Meetings & QBRs") added to the founder-approved grouped order list. Nothing removed.

**Not built: `/meetings/new`.** The spec has no manual "create a meeting" flow: meetings come from connected calendars, and the thing you create is a QBR (`/meetings/qbr/new`, linked from the index). So `/meetings/new` stays a 404. Say if you want a manual meeting form; it would need a spec decision.

**Evidence.**
- `src/modules/meetings/__tests__/list-index.test.ts` (5 tests): Admin sees all including an unmatched call; CSM sees only their book; CS Leader sees the whole workspace (leaders hold `accounts:view` on ALL, so this matches Admin); account filter; no cross-workspace leak. Briefs are not listed as QBRs.
- `src/config/__tests__/features.test.ts`: new milestone-12 rows for all four roles (52 tests pass).
- `e2e/fix-meetings-index.spec.ts` (8 tests, desktop): the sidebar link opens `/meetings` and the page lists meetings and QBRs for **Admin, CS Leader and CSM**; the Generate-a-QBR link reaches `/meetings/qbr/new`; Aisha (CSM) does not see Leo's Brightwell meeting; a Viewer sees the index with no QBR button; the link is on all 18 screens; the Account 360 tab works; axe finds no blocking violations on `/meetings`.

## 2. Today vs Renewals

**Findings.** The data agrees: 12 accounts, same dates, $529,800 (checked on the Docker database). The mismatch was in how each screen read it:
- Today's "next 90 days" list read **`Account.renewalDate`** (a copy on the account) for accounts the member **owns**. The Renewals page reads **Renewal records** for everything the member's permissions allow.
- Today's own "Renewals in 30 days" card used the Renewals page function (permission scope), so the card and the list **on the same page** disagreed (the card said 3 while the list said 0).
- The demo Admin owns no accounts (35 are unowned, 37 belong to two CSMs), so "only for my accounts" (spec §5) gives 0 on Today while the Renewals page shows 12. That scope difference is by design; what was wrong was the different source, the self-contradicting card, and no explanation.

**Fix.**
- One definition of the window: `openRenewalWindow(asOf, days)` in `src/modules/renewals/read.service.ts` (open stage, date from today to today + days). `listRenewals` and Today both use it.
- Today's renewals list now reads Renewal records on the member's own accounts (own, plus the unowned pool for TEAM scope), one item per account.
- Today's 30-day card uses `countMyRenewalsDue` (same query, same scope), so card and list agree. Its caption now reads "On your own accounts".
- When the member's own list is empty but the Renewals page has some, Today says so: "None of your own accounts renew in the next 90 days. The Renewals page lists N across everyone you can see."

**Evidence.**
- `src/modules/today/__tests__/renewals-consistency.int.test.ts` (5 tests) keeps the two in step: for a CSM, Today's list equals the Renewals page account for account; an account whose own `renewalDate` is empty still shows (the Renewal record is the source); the 30-day card equals the page's 30-day total for three members; a TEAM-scope CSM sees the unowned pool on both; Admin gets 0 on Today = the page filtered to the same owner, while the page lists 4.
- `e2e/fix-today-health.spec.ts`: Leo's Today list count equals his `/renewals?days=90` row count, and his card equals `/renewals?days=30`; Admin's Today shows 0 with the note quoting the Renewals page's real total.

**Existing test touched (arrangement only).** `src/modules/today/__tests__/today.int.test.ts` built its renewal only as `Account.renewalDate`, which Today no longer reads. I added a contract and a Renewal record for the same account and date. Every assertion is unchanged. Please look at this one; CLAUDE.md asks for a flag when an existing test is changed.

**Observed, not changed.** The other Today cards ("Accounts at risk", "ARR at risk") say "in your assigned book" but read the permission scope, so an Admin sees workspace-wide numbers there while the renewals card is now own-book. Same family of inconsistency; left for a decision.

## 3. Unscored accounts

**Finding: by design, not a bug, and not "insufficient data".** The 12 unscored accounts are exactly the 12 accounts in lifecycle stage **LOST** (churned customers). The nightly signals/health pipeline, `healthOverview`, every agent trigger and Today all skip LOST accounts on purpose. All 60 non-lost accounts have a score; the 12 LOST ones each have 181 days of usage and 0 snapshots. The Health page counts only non-lost accounts in its bands, so those 12 appeared nowhere on it, and the Accounts list and Account 360 header called them "Not scored yet", which wrongly implies a score is coming.

**Fix.**
- `listUnscoredAccounts` (`src/modules/health/service.ts`): every account in the member's book with no score, each with a plain-language reason. Two kinds: `LOST` ("Lost account. Health is only calculated for active customers, so it is not scored.", with the churn date when recorded) and `AWAITING_FIRST_SCORE` (an active account the current model has not scored yet).
- Health page: the old one-line "N accounts have not been scored yet" is replaced by a **Not scored (N)** section listing each account, its kind and its reason. It is open when 15 or fewer and collapsed otherwise, capped at 200 rows with a notice.
- Accounts list and Account 360 header: lost accounts read **Not scored (lost account)**; active ones keep "Not scored yet".
- Nothing here is a score; missing data lowers nothing (rule 4).

**Evidence.**
- `src/modules/health/__tests__/unscored-accounts.int.test.ts` (2 tests): lost and awaiting accounts are listed with the right kind, reason and churn date; archived accounts are not; the awaiting count equals `healthOverview().unscored` and every unscored account is accounted for.
- `e2e/fix-today-health.spec.ts`: the Not scored section's row count equals the number of non-archived LOST accounts in the database (12 on the demo data) with the reason text on the first row; `/accounts?stage=LOST` shows "Not scored (lost account)" and no "Not scored yet".

**Observed, not changed.** `getActiveModel` creates the default health model lazily, so two concurrent first calls in a brand-new workspace can race. The Health page already calls it from two places at once; a workspace normally has a model after its first nightly run. My new test takes the model first to stay deterministic.
