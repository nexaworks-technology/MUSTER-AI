## 2. Batch API (`runAgentsBatch`, `collectBatches` in `src/modules/agents/executor.ts`)

Bulk jobs are submitted as **one** Message Batches request per pass (50% discount, results within 24 h; usually far less). Each submitted run is `RUNNING` with its `batchId` (the batch `custom_id` is the run id) and the input payload (ids only). A repeatable worker job, `agents.collectBatches` (every 5 minutes), polls and finishes finished batches. A batch result is finished by the **same** `execute` code as a real-time answer: schema parse, the one repair call, citation checker, forbidden numbers, persist, side effects. Before that, the run's records are rebuilt and must hash exactly as at submit time; if the account changed while the batch ran, the run is `SKIPPED (STALE_BATCH_INPUT)` and the next sweep asks again, so an answer is never checked against different records than it was written from.

Goes through batches: Health Analyst sweep, Renewal Manager sweep, Expansion Finder sweep, Watcher extraction backfill and re-extraction, Promise Keeper sweep, Onboarding Manager and Adoption Coach sweep.

Stays real time (interactive, or a person or a deadline is waiting): Ask AI, approvals and in-app actions (check-in, outreach, QBR generation), the event-driven narrative on a band change, champion-guard and support-risk (event-driven), the pre-call meeting brief (needed minutes before the call), and the weekly Leader Reporter digest (one call a week; it was never a sweep). A provider without batch support (and the recorded one in tests) falls back to real time with no change in behaviour.

Cost of the design: narratives, plans and extractions from the sweeps now arrive after the batch completes (typically well under an hour) rather than within the sweep. The batch endpoint was exercised only against fakes in tests. **No live batch has been submitted**; the SDK calls follow its types, but a first real batch is the one thing to watch.

**Evidence:** `cache-batch.test.ts` (one `batches.create` call with every request, per-tier model, results mapped back with tokens and failure reasons); `executor-cost.int.test.ts` (3 accounts, one unchanged: exactly 2 in ONE batch, 0 real-time calls; runs wait as `RUNNING`; collect finishes them with output, tokens, cache tokens; a made-up quote is `UNCITED` and writes nothing; one errored item fails only its run; bad text gets the one repair call; stale input skipped; no batch support falls back; a re-run while pending submits nothing); `sweeps-batch.int.test.ts` (the real Promise Keeper sweep: one batch of two, 0 real-time calls, no task until collect, then both chase tasks written).

## 3. Prompt caching

`messageParams` (shared by real-time calls and batch entries) sends the system prompt as a block with `cache_control: ephemeral`. The per-call records are deliberately **not** marked: they are unique per call, and a cache write costs 1.25× input, so marking them would add a surcharge and never be read. Each run records `cacheReadTokens` and `cacheCreationTokens` (real time and batch); they show on the run page and in the cost estimate. Tests prove the marker is on the system block and not on the user content, that usage counters are read (null counts as 0), and that batch entries carry the same marker.

**What it actually saves (measured):** Haiku 4.5 only caches a prefix of 4,096+ tokens, and none of our prompts reach it. In the live extraction eval the **Haiku run read 0 cached tokens**; the **Sonnet run read 17,946 of its 25,266 tokens from cache** (Sonnet's minimum is lower). So caching is nearly inert on the cheap tier that now carries almost everything. It helps the Sonnet jobs (Ask AI answers, the weekly digest). Also, a system prompt that embeds the account name differs per account, so it only repeats within one account's retries, its repair call and Ask AI's multi-step loop. Making the shared part identical across accounts would mean moving the prompt variables out of the system text, which changes what the model sees and every recording key; not done.

## 4. Change-only jobs

`ExecutorDeps.skipIfUnchanged` (on by default in `runAgentsBatch`, so every bulk sweep): when the exact records and variables a run would send hash identically (`AgentRun.inputHash`) to the agent's last **successful** run on the same account, with the same agent version and prompt version, there is no model call, no run row and no batch entry, and the outcome says `unchanged`. A person's own request is not gated, so asking again always answers. A changed record, a new agent version or a new prompt version runs normally. Due items count because they are part of the records (dates and statuses in the bundle).

Honest limit: the sweeps already fired only on change (a band or top-reason change, a new signal, an unread message) and were idempotent per trigger, and their bundles carry the trigger's record ids. So this gate is a backstop that makes "same inputs, no call" a guarantee; I have **no production data** to say how many calls it will remove.

**Evidence:** `executor-cost.int.test.ts` (second night, same records: provider not called again, one run row only; asking directly still runs; after a change it runs; in a batch the unchanged account is excluded).

## 5. Budgets and the estimate

- **Monthly token budget** per workspace: `ai.monthlyTokenBudget` in workspace settings, default **10,000,000** tokens (about half of $40 at Haiku prices, leaving room for Sonnet work and evals). Counted per calendar month in the workspace's time zone, all token kinds: input, output, cache reads and writes, and Ask AI planning.
- **80%:** one in-app notification per Admin and CS Leader per month (`AI_BUDGET_SOFT`, opens Pilot metrics) and a banner there.
- **100%:** every job except Ask AI is skipped (`SKIPPED`, code `MONTHLY_BUDGET`, reason in the run) before any model call; Ask AI keeps working (`ESSENTIAL_AI_JOBS` is one list). The daily budget that already existed is unchanged.
- **Estimate:** `src/config/ai-pricing.ts` holds the prices (Haiku $1 in / $5 out, Sonnet $3 / $15 per million tokens; batch ×0.5; cache read ×0.1; cache write ×1.25). Pilot metrics › **AI usage this month (estimate)** shows tokens against the budget, the estimated cost, a per-tier table, batched runs and cache-read tokens, and the label: "Estimate … Not an invoice." If you point a tier at another model, or prices change, edit that file; nothing else holds a price.
- **Found and fixed while testing:** Ask AI's planning calls ran outside the executor, so their tokens were on no run and the budget could not see them; in the live Haiku eval they were most of an Ask's input tokens. They are now recorded on the answer's run (`planningInputTokens`, `planningOutputTokens`) and priced at the fast tier, where planning runs.

**Evidence:** `ai-pricing.test.ts`, `budget.int.test.ts` (month window and tier table, batch at half, planning counted and priced at fast, levels at 80 and 100 %, alert once per month per leader and again next month, a non-essential agent skipped with no call while `ask-ai` still runs), `ask-loop.int.test.ts` (planning tokens recorded on the run), `e2e/ai-cost-pilot.spec.ts` (the section, the 10,000,000 default, the estimate label, no alert when unspent).
