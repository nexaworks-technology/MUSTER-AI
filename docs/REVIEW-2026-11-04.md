### SHOULD-FIX

**S1. Raw usage events outlive aggregation: 7 days after success, 30 after failure, in Redis.** *(contradicts Q-33 / D-23 / D-110 and M6-LOG)*
- *Where:* `src/lib/jobs/queues.ts:45–46` sets `removeOnComplete: { age: 7 * 86_400, count: 10_000 }` and `removeOnFail: { age: 30 * 86_400 }` as the queue default. `usage-api/receive.ts:65–70` adds `usage.aggregate` with only `jobId`, `attempts`, `backoff`, so it inherits both.
- *Evidence:* after the e2e run, Redis held three completed jobs `nexaworks-e2e:sync:usage-<integration>-abf2a47c…`. One had `name: usage.aggregate`, `finishedOn` set, `ttl: -1` (BullMQ removes by age later), and `data` = `{workspaceId, integrationId, batchKey, events: [8 events]}`. The first event is `{kind: "track", userId: "raj.patel@pinecrest-health.test", groupRef: "pinecrest-health.test", at: …, messageId: "demo-usage-pinecrest-001", event: "Session Started"}`. So raw events, including an email address used as a user id, persist after being folded.
- *What the record says:* Q-33 (founder-approved): "raw events are held in the queue only until aggregated, then discarded" (`QUESTIONS.md:49,90`); D-110 ("No raw events, anywhere but a queue payload"); M6-LOG ("events live only in this job's payload"; `usage.aggregate` docstring "then let the events go"). The no-raw-event-**table** claim is true; the discard-after-aggregation claim is not.
- *Why it matters:* the privacy statement M12 is to put in the setup guide (`M12.md:82`) says no raw history is kept. A failed job (e.g. an unmatched-account bug) would keep the payload 30 days.
- *Fix (small):* `removeOnComplete: true` and a short `removeOnFail` for `usage.aggregate`, plus a test asserting the enqueue options; purge existing completed `usage-*` jobs; until then reword D-110/M6-LOG.

**S2. `UsageIngestBatch` has no write attack in the M6 tenant suite, but M6-LOG #12 says it is covered.**
- *Where:* `tenant-isolation-m6.int.test.ts` covers template, plan, step and goal only (grep for `usageIngestBatch` in it: none). The batch appears only in `ingest-api.int.test.ts:185,195–198` as read/visibility checks. M6-LOG row 12: "B1 adds `UsageIngestBatch` to the registry … and the usage key path".
- *Is isolation broken?* No: my scratch attack (§2) shows 0/0 on update and delete from A, intact B row, FK refused. The registry test checks RLS/FORCE/policy for the model. This is test strength and log accuracy, the same class as the M3 review's S1.
- *Fix:* add `UsageIngestBatch` to `tenant-isolation-m6` with a real-field update (`events`) plus own-row control, a delete, and the composite-FK case. Correct the M6-LOG wording.

**S3. Seven deferrals have no home or a wrong home in the milestone docs.** All are listed in §5 with ❌: live checks for M5/M6 connectors, live Resend, Docker #16, Q-48 (M8), Q-54 (M12), call-derived goals/promises in the handoff (M9), Q-47.

**S5. "Write-back stays fake-transport-only" is a convention, not a code guard.** *(decision-sized)*
- *Where:* `writeback.service.ts:19` ("pushes are exercised only against the fake transport (founder D2)"), D-89, M5-LOG ("live write-back is DEFERRED by founder D2 regardless"). The push is `loadConnection` → `transportFor(provider)` → the live transport in production; HubSpot and Salesforce declare the owner field and implement `push`. Nothing in code refuses a live push; what protects it is the Admin switch, the field list and an approval. `INTEGRATIONS_TRANSPORT=fixture` is refused in production, but the opposite guard (refuse live write-back until D2 is lifted) does not exist.
- *Fix:* name it as its own decision. Either add an env guard (e.g. refuse `writeBack.push` over the live transport unless an explicit setting is on) or amend D-89/M5-LOG to say the gate, not the transport, is the control.
