# DECISIONS

Architecture and process decisions. Each entry gives the decision, the alternatives rejected and why. Stack decisions come from
`CLAUDE.md` and are recorded here so later changes have a trail. Changing any **[STACK]** item needs founder approval.

| ID | Date | Decision | Rejected alternatives & why |
|---|---|---|---|
| D-01 [STACK] | 2026-10-31 | **One Next.js (App Router) app + one worker process in a single pnpm package** (`src/app`, `src/modules`, `src/worker`). A modular monolith with module boundaries enforced by lint (modules import each other only via `service.ts`). | *Turborepo/pnpm workspaces*: extra build tooling with no deployment benefit for one team. *Microservices*: forbidden by CLAUDE.md; tenant/audit consistency is far simpler in one DB transaction. |
| D-02 | 2026-10-31 | **Background work runs in a dedicated BullMQ worker** (`src/worker/index.ts`, run with `tsx` in dev, compiled in prod), sharing modules with the web app. | *Jobs inside Next.js route handlers/cron*: request timeouts, no retries/backoff, no concurrency control. *Hosted serverless queues*: second platform, no gain over Redis already in the stack. |
| D-03 | 2026-10-31 | **Tenant isolation in three layers:** scoped Prisma client extension (primary, by construction) + Postgres RLS with `FORCE` on a non-owner role (defense in depth, satisfies spec §6N3 "at the database level") + composite `(workspaceId, id)` foreign keys. | *App-only filtering*: one forgotten `where` leaks data. *Schema- or database-per-tenant*: migrations × N, connection sprawl, overkill for 50–2,000-account customers. *RLS only*: errors surface late; the scoped client fails fast in dev. |
| D-04 | 2026-10-31 | **Health is deterministic TypeScript** (components → pillars → overall) with piecewise-linear curves stored in a versioned `HealthModel`. The "AI-proposed model" is a **deterministic grid search scored by back-test**. The LLM only explains. | *LLM scoring*: unexplainable, non-reproducible, violates "LLM never invents the number". *Trained ML (logistic regression / GBM)*: too little labelled history per workspace (often < 20 churns), weights hard to explain to a CSM, and per-workspace training adds MLOps. Grid search over 6 weights is explainable and reproducible. |
| D-05 | 2026-10-31 | **Signals = deterministic rules. LLMs produce only `Extraction`s** (with verbatim quotes), which rules convert to signals. | *LLM creates signals directly*: cannot guarantee evidence, dedupe or false-alarm tuning, and makes the AI-accuracy view meaningless. |
| D-06 [STACK] | 2026-10-31 | **In-house `defineAgent` framework on the official Anthropic SDK.** Single-shot structured output via the Messages API's `output_config.format` from the Zod schema (D-35), then Zod-parse, then citation validation. Ask AI is the only multi-step tool-using agent. | *LangChain / other agent frameworks*: second framework (CLAUDE.md forbids), opaque retries. *Autonomous agent loops for every agent*: unbounded cost, harder to audit; each specialist has one job and one run. |
| D-07 [STACK] | 2026-10-31 | **Auth.js with credentials + Google and *database* sessions.** Auth.js's credentials provider natively supports only JWT sessions. We keep the database strategy by creating the `Session` row ourselves on successful credentials sign-in (custom `jwt.encode`/`decode` override returning the DB session token, cookie set by Auth.js), and test it explicitly in M1. | *Switch to JWT sessions*: contradicts CLAUDE.md, and revocation (user removed from workspace) becomes delayed. *Drop credentials login*: contradicts CLAUDE.md. *Lucia / better-auth*: stack change. |
| D-08 | 2026-10-31 | **Auth.js's linked-OAuth model is named `AuthAccount`.** A thin adapter wrapper around `@auth/prisma-adapter` maps it. Our customer model keeps the spec's name `Account`. | *Rename our model `CustomerAccount`*: diverges from spec language used across UI, docs and prompts. *Separate auth database*: needless complexity. |
| D-09 | 2026-10-31 | **Money is `BigInt` minor units + ISO currency**, aggregated only within one currency (Q-12). | *Float/Decimal in JS numbers*: rounding errors in ARR waterfalls. *Implicit FX conversion*: invented data (Rule 4). |
| D-10 | 2026-10-31 | **One customer-send choke point:** `outbound.dispatch()` is the only importer of the customer email transport (ESLint restricted import + import-graph test). Guards and the sensitive-topic gate run there for every send, including approved ones (suppression). | *Guard checks in each caller*: easy to forget one path (campaigns, plays, inbox). |
| D-11 | 2026-10-31 | **"No orphan AI text" is enforced by the database:** every AI-originated row has `origin='AI'` and a non-null `agentRunId` (CHECK). UI renders AI text only through `<AiText>`, which requires a SUCCEEDED AgentRun. | *Convention only*: Rule 5 would depend on reviewer memory. |
| D-12 | 2026-10-31 | **Citation validation is mechanical:** cited ids must be in the run's ContextBundle, and quotes must be verbatim substrings. Agents declare `forbiddenNumericFields`, which are overwritten from deterministic code. | *Trusting model citations*: models can cite plausible but non-existent ids. |
| D-13 | 2026-10-31 | **Ask AI numbers must appear in tool output**, validated before render. The answer is rejected otherwise. | *Let the model compute sums*: arithmetic errors presented as facts. |
| D-14 | 2026-10-31 | **`pnpm gate` = typecheck + lint + test + build** (as CLAUDE.md). `pnpm test:e2e` is required at the end of each milestone and in CI, but is not part of the per-commit gate. | *E2E inside gate*: needs browser + running services for every commit; slows thin-slice commits. Milestones still cannot be marked done without it. |
| D-15 | 2026-10-31 | **No separate spec "Phase 0" canned prototype.** The seeded demo workspace runs real code paths from M2 onward and serves design-partner demos. | *Canned clickable prototype with "Ask AI (canned)"*: conflicts with CLAUDE.md Rule 6 (no hard-coded demo data in features) and would be throwaway work (Q-29). |
| D-16 | 2026-10-31 | **Milestone placement within V1 (no scope change):** Slack in M5 (with integrations core), Campaigns in M8 (reuses plays' outbound pipeline), Leader Reporter in M11 (spec §6L requires weekly reporting even though §8's Phase 1 agent list omits it; Q-04), Outreach + Digital CSM in M8 in "limited form" per spec §8. | Putting Campaigns in M9 would overload the conversations milestone. Leaving Leader Reporter to Phase 2 would leave §6L/§6E13 without a home. |
| D-17 | 2026-10-31 | **Integration build order:** CSV (M2) → HubSpot, Salesforce, Stripe, Chargebee, Slack (M5) → Usage API/Segment, Mixpanel, Amplitude (M6) → Zendesk, Freshdesk, Gmail/Outlook (M9) → calendars, Fireflies/Gong/Zoom (M10). Each lands with the feature that first uses its data. | *All adapters in M5*: a huge milestone, and data with no feature to use it until later. |
| D-18 | 2026-10-31 | **Local object storage is MinIO in docker compose** (S3-compatible, same storage module as prod). | *Local filesystem driver*: a second code path. *Real S3 in dev*: needs cloud credentials to run tests. The CLAUDE.md "DB up" command needs `minio` added (Q-17). |
| D-19 | 2026-10-31 | **`RecordedProvider` for AI exists only for tests/demo replay** (refused at boot in production). Without an API key, the product shows "AI is not configured", never fake output. | *Mock provider in dev by default*: mock data in a production code path (Rule 6). |
| D-20 | 2026-10-31 | **Today ranking is a deterministic formula** (money weight × urgency) with stored reasons. | *LLM ranking*: non-reproducible ordering, cannot explain "why is this first". |
| D-21 | 2026-10-31 | **Point-in-time reconstruction for back-tests** from timestamped records. `StakeholderRole` keeps validFrom/validTo history, and snapshots are never overwritten. | *Back-test on current-state data*: look-ahead leakage inflates results and misleads buyers. |
| D-22 | 2026-10-31 | **Transactional outbox** (`OutboxEvent`) for domain events → BullMQ. | *Enqueue directly after commit*: lost events on crash. *Enqueue inside the transaction*: phantom jobs on rollback. |
| D-23 | 2026-10-31 | **Usage is stored as daily aggregates** (account, user, feature). Raw events are not stored. | *Raw event store*: warehouse territory (Phase 2 connectors), large storage, not needed for CS-language adoption views. |
| D-24 | 2026-10-31 | **Agent behaviour lives in code (registry) and per-workspace settings in `AgentDefinition` rows**, so custom agents (Phase 2) can plug into the same table (`isCustom`). | *Agents fully in DB*: prompts and schemas unversioned outside git. |
| D-25 | 2026-10-31 | **Prompts are versioned `.md` files** with frontmatter, validated at boot against agent definitions. A version bump needs a golden/eval note in the milestone log. | *Prompts inline in TS*: no clean version trail per AgentRun. |
| D-26 | 2026-10-31 | **Structured logging with pino + redaction.** AI content and email bodies are never logged; ids/token counts only. | *console logging*: no redaction, so Rule 9 risk. |
| D-27 | 2026-10-31 | **New pnpm scripts are added to CLAUDE.md's Commands section in the same commit that creates them.** Planned: `jobs:nightly` (M3), `eval` (M4), `seed:replay` (M11), `seed:synthetic` (M12). | Documenting them before they exist would make CLAUDE.md untrue. |
| D-28 | 2026-10-31 | **Seed data uses the reserved `.test` TLD for every email/domain** and a fixed PRNG + `SEED_TODAY`. Derived data (health, signals, extractions, agent runs) is produced by running the real pipeline, never inserted. | *Hand-inserted health/signals*: hard-coded demo numbers in features (Rule 6), and they would not prove the engine works. |
| D-29 | 2026-10-31 | **Phase 2/3 seams only:** adapter interface (more connectors), `AgentDefinition.isCustom` (custom agents), `Document.narrative` blocks (richer Docs), `Integration.writeBack*` (deeper write-back). Nothing more is built early. | Building custom agents, the SDK, SSO/SCIM etc. now violates spec §8 phase discipline. |
| D-30 | 2026-10-31 | **The Outreach Agent starts in M4 in basic form** (one draft email for one CSM-requested check-in, always DRAFT_FOR_APPROVAL), so the approval → dispatch path is proven with real AI drafts early. M8 extends the same agent with play-step intents, voice samples and per-step levels. | *A separate small `checkin-draft` agent*: an agent not in the spec (spec §6E has exactly 13 + Ask AI). *No AI draft until M8*: the M4 demo would approve only hand-written drafts. |
| D-31 | 2026-11-02 | **Local services: `docker-compose.yml` is canonical** (Postgres 16, Redis 7, MinIO, `app_user` role via `docker/postgres/roles.sql`, explicit project name). **Documented fallback without Docker:** `pnpm services:native` starts Homebrew Postgres/Redis/MinIO and applies the *same* `roles.sql`. This machine has no Docker, so M1 is built and tested on the fallback (founder-approved 2026-11-02). Compose credentials come only from `.env` (no defaults in the file). `minio/minio` is no longer published on Docker Hub, so compose uses `chainguard/minio:latest`. **Known risk:** native Postgres here is **14**, compose specifies **16**. No Postgres-16-only feature may be used without a DECISIONS entry. | *Docker only*: nothing could be verified on this machine. *Fallback with its own SQL*: the two setups would drift. *Defaults for passwords in compose*: committed credential values (Rule 9). |
| D-32 | 2026-11-02 | **Pinned toolchain for M1:** Next.js 16.4.3, React 19.3.1, TypeScript **5.9.3** (typescript-eslint 8.72 supports < 6.1, so not TS 7), ESLint **9.39.5** (not 10, for plugin compatibility), **Prisma 6.19.3** (npm `latest` is an 8.0 RC; Prisma 7 is outside `@auth/prisma-adapter`'s declared peer range), **Auth.js `next-auth@5.0.0-beta.32`** (M1 requires v5; v5 is still tagged beta, and v4 is the `latest` tag), Zod 4, Vitest 5, Playwright 1.64. All exact-pinned. | *Newest majors everywhere*: a release candidate as ORM, and lint tooling that does not support the compiler. *Auth.js v4*: weaker App Router support and contradicts M1. |
| D-33 | 2026-11-02 | **How D-07 is implemented:** the database `Session` row is created in `callbacks.jwt` (trigger `signIn`, provider `credentials`), and `jwt.encode` returns its token, which Auth.js writes into its standard session cookie. `jwt.decode` returns null. This replaces M1.md's "signIn callback + `cookies().set`" because Auth.js already sets the cookie from `encode`, so no second cookie writer is needed. **Google** is always registered from env (Auth.js forbids a credentials-only provider list with database sessions). When unconfigured, its button is hidden and its routes 404. Google sign-in **never creates users**: only existing accounts may use it. | *Manual cookie in the signIn callback*: two code paths writing the session cookie. *JWT sessions*: contradict CLAUDE.md. *Let Google auto-create users*: anyone with a Google account could create a user with no workspace. |
| D-34 | 2026-11-02 | **Auth events are audited per workspace:** `auth.signed_in`, `auth.signed_out` and `auth.failed` (wrong password for an existing user) are written to the AuditLog of **every workspace the user is an active member of**. A failed sign-in for an **unknown email** is not written to any tenant's log (there is no tenant to attribute it to). Audit writes for auth never block sign-in; failures are logged. Passwords are never stored in audit rows. | *A global (non-tenant) audit table*: breaks "every domain record is workspace-scoped" and the tenant's own export. *Logging unknown-email attempts into some tenant*: leaks attempts between tenants. |
| D-35 | 2026-11-02 | **Structured AI output uses `output_config.format` (`client.messages.parse` + `zodOutputFormat`), not a forced tool call.** Current models (e.g. Claude Opus 5.5 / Sonnet 5.5) return a 400 for forced `tool_choice` (`any`/`tool`). The parsed output is still Zod-validated by us, and a refusal or schema failure yields `output: null` (never a guess). Model names stay env-only per tier. Refusal fallbacks (`fallbacks` parameter) are decided in M4, together with the first agent, because they depend on which models are configured. | *Forced tool use* (as first written in ARCHITECTURE §1.3): rejected by the API on current models. *Free-text JSON parsing*: no schema guarantee. |
| D-36 | 2026-11-02 | **The test database is migrated, never reset, by tooling.** `pnpm test` and `pnpm test:e2e` run `prisma migrate deploy` on the `_test` database. Tests create uniquely named workspaces and assert only inside them. Prisma refuses `migrate reset` when an AI agent runs it, which is correct, so a full reset of the test database is a human-only action. | *`migrate reset` per run*: destructive and blocked for agents. *Truncate between tests*: AuditLog is append-only by design. |
| D-37 | 2026-11-02 | **e2e runs the app with `next dev` against the `_test` database**, migrated and seeded with both tenants in Playwright's global setup. The production server refuses the log-only email transport (env schema), and the invitation flow reads its link from `.dev-mail/`. No other `next dev` may run in the folder during e2e. A production-build e2e arrives with the M12 staging smoke test. | *Allow the log transport in production for e2e*: weakens a production guard. *Mock email in e2e*: the flow would no longer be tested end to end. |
| D-38 | 2026-11-02 | **pnpm install scripts are allow-listed** in `pnpm-workspace.yaml`: Prisma (client, engines, CLI) and esbuild only. `msgpackr-extract` (an optional native accelerator pulled in by BullMQ) is denied, and msgpackr uses its pure-JS path. | *Approve every requested build*: more install-time code execution for no functional gain. |
| D-39 | 2026-11-02 | **Each Settings page checks access itself** (`requireSettingsAccess`) in addition to the layout, because App Router pages render concurrently with their layout. Without the permission, the route is a 404 (matching the hidden nav). | *Layout-only check*: the page's data loader still ran (it was blocked by the service permission check, but it logged a ForbiddenError). |
| D-40 | 2026-11-02 | **Deferred to M3: the lint rule requiring `${ctx.workspaceId}` in tagged `$queryRaw`** (ARCHITECTURE §7.1). Interim protection, already in place and tested: the scoped client runs every tagged raw query inside the `app.workspace_id` transaction, so RLS still limits it to the caller's workspace. Unsafe raw methods are refused. M3 introduces the first raw aggregate SQL, so the rule lands with it. | *Build the rule now with no raw SQL to apply it to*: untestable against real usage. |
| D-41 | 2026-11-02 | **Book scope TEAM = the member's own accounts plus unowned accounts** (the shared long-tail pool). ARCHITECTURE §7.2 names a TEAM scope, but no team model exists in the spec or the plan (Q-35). OWN = owned by me, ALL = everything. | *TEAM = ALL*: a CSM widened to "Team" would see colleagues' books without anyone deciding that. *TEAM = OWN*: the setting would do nothing. |
| D-42 | 2026-11-02 | **Accounts list paging uses an opaque cursor over a fully deterministic order** (sort field with NULLs last, then id). The cursor encodes an offset. Prisma's id-cursor paging is unreliable when the sort field is nullable (ARR, last touch), and offsets over a total order never skip or repeat rows at our scale (50–2,000 accounts). Without revenue access, sorting by ARR falls back to the default order, because sort order would leak relative contract values. | *Prisma `cursor` on id*: breaks with nullable sort columns. *Client-side paging*: forbidden for this screen. |
| D-43 | 2026-11-02 | **Transcript fixtures are composed deterministically, not hand-written.**<br>• `prisma/seed/fixtures/make-transcripts.ts` builds 14 transcripts of 1,400–2,200 words from a curated neutral line bank, inserts every planted line verbatim, and writes them to committed files that the seed reads.<br>• The bank avoids every risk cue (competitors, money, cancellation, complaints, dated commitments), so the 8 neutral transcripts are true negatives for M9 extraction.<br>• The Brightwell post-call transcript (2026-11-02) is kept as an upload-only fixture for the M10 demo and is not seeded.<br>• **Last touch** is defined as the latest email, chat, call or meeting interaction. Support tickets are not a CSM touch. | *Hand-writing about 25k words of dialogue*: no added value for tests. *Short stub transcripts*: SEED_DATA asks for realistic length. *Counting tickets as touches*: an account with only open support tickets would look actively managed. |
| D-44 | 2026-11-02 | **Timeline = a source registry plus a pure keyset merge.** Each module's `service.ts` exports its own timeline items (contacts, billing, usage change points, support, conversations, tasks, notes). A small `timeline` module checks access once and runs the sources in parallel. `mergeTimeline` orders by (at desc, key asc), and the cursor is that pair, so pages never repeat or skip, even when new items arrive. Each source fetches page + 50, so ties at the cursor are never lost. Usage appears as **change points** (±30% against the previous four weeks, one per run), not daily rows. Money in titles only with revenue access. M3+ registers signals, health, agent actions and meetings. | *Timeline assembled inside `accounts` by querying other modules' tables*: breaks module boundaries. *Offset paging*: shifts when new items arrive. *A denormalised timeline table*: a second copy of every record to keep in sync. |
| D-45 | 2026-11-02 | **Segment DSL = an AND of typed conditions over an Account field whitelist** (text: eq / in / contains / empty; enums: eq / in; dates: before / after / between / within next N days / older than N days / empty; ARR in base-currency units: ≥ / ≤ / between / empty; owner: member or none), at most 20 conditions. It is Zod-validated on save and again on use: a stored filter that no longer validates is shown as unusable, never widened. ARR conditions need revenue access, because filtering by ARR would leak values. Evaluation always adds the member's book scope through `scopedDb`. Segments are shared workspace-wide; the creator, or an Admin or CS Leader, deletes them. The health filter is added in M3. | *Free-form Prisma where in JSON*: arbitrary field access, including tenant columns. *OR/nesting now*: more than the spec's "group in a few clicks" needs. Kept for later behind the same schema version. |
| D-46 | 2026-11-02 | **Upload safety (the M1 deferral) and a `data:import` permission.**<br>• Allowed types per purpose live in `src/config/uploads.ts`: contract documents are PDF, .docx, PNG, JPEG or .txt; CSV import is CSV only. The limit is 25 MB.<br>• Content is checked with **`file-type@22.1.1`** (pinned; chosen over the newest release so it has a few weeks' track record): binary types by magic bytes; text types must be clean UTF-8 with no control bytes. The browser's MIME claim is ignored, and filenames are sanitised.<br>• Storage keys are `ws/<workspaceId>/files/<uuid>`, generated by us and never sent to the browser.<br>• Upload goes only through `POST /api/files`, download only through `GET /api/files/[id]/download`, always as an attachment with `nosniff`. Contract documents need revenue access and the account in the book. CSV imports need **`data:import`** (Admin and CS Leader), a permission ARCHITECTURE §7.2 lacked; it was added to the matrix and its test.<br>• Malware-scanner hook: a dev/test no-op marks files clean. **In production files stay PENDING and unusable until a scanner is configured** (Q-18, M12). A rejected file never reaches storage (tested). | *Trusting the extension or the browser's MIME type*: trivially spoofed. *Presigned S3 links*: a URL that works for anyone holding it. *Letting every CSM import CSVs*: bulk writes to the shared Account Graph belong to data owners. |
