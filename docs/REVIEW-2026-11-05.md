## 3. The Back-Test Exclusion

### Robustness & Fragility Assessment
In M9 Session A (`3985165`), new text, promise, and people signal rules were found polluting `riskSignalsAsOf` during the renewal confidence back-test. The fix added `M9_RULES_OUTSIDE_THE_BACKTEST` in `src/modules/signals/rules/as-of.ts`.

Lines 46–53 of `src/modules/signals/rules/as-of.ts`:
```ts
export const RENEWAL_RISK_RULE_KEYS: readonly RuleKey[] = RULES.filter(
  (r) =>
    r.polarity === "RISK" &&
    r.category !== "OUTSIDE" &&
    !r.dormantReason &&
    !RESTATES_OTHER_FACTORS.has(r.key) &&
    !M9_RULES_OUTSIDE_THE_BACKTEST.has(r.key),
).map((r) => r.key);
```

**Risk Assessment: SHOULD-FIX (High Fragility).**  
Because `RENEWAL_RISK_RULE_KEYS` is built by filtering the global `RULES` catalog with an exclusion blacklist (`!M9_RULES_OUTSIDE_THE_BACKTEST.has(r.key)`), any new rule added in M10 (such as `no_meeting_in_x_days` when activated, or new meeting/sentiment risk signals) or M11 will have `polarity === "RISK"`, `category !== "OUTSIDE"`, and will not be in `M9_RULES_OUTSIDE_THE_BACKTEST`. Consequently, **it will silently enter `RENEWAL_RISK_RULE_KEYS`**, silently altering the inputs of `riskSignalsAsOf` and corrupting the pre-registered renewal confidence back-test calibration without raising any error.

**Construction-Level Alternative:**  
Convert the back-test risk-rule set to an explicit, pinned allowlist:
```ts
export const RENEWAL_BACKTEST_RULES_V1: readonly RuleKey[] = [
  "health_band_drop",
  "adoption_drop",
  "seat_utilization_drop",
  "feature_adoption_low",
  "login_drop_extreme",
  "power_user_quiet",
  "champion_departure",
  "contract_value_risk",
  "nps_detractor",
] as const;
```
Pair this with an automated test in `as-of-m9.test.ts` asserting that `RENEWAL_RISK_RULE_KEYS` matches `RENEWAL_BACKTEST_RULES_V1` exactly, failing immediately if new rules are added to the catalog without an explicit version bump.

## 4. Q-80 — Sensitivity Lookback Semantics

### M4 Design & Current Code Behavior
In M4 (`M4.md:84`), `detectSensitive(text, extractions, stepTags)` was designed to catch sensitive topics (cancellation, legal, complaints, pricing) to prevent automated outbound contact. In M4, extractions were created only on incoming items for the immediate triage event.

In `src/modules/approvals/lifecycle.ts:102–110`:
```ts
  const extractions = await db.extraction.findMany({
    where: {
      accountId: account.id,
      kind: { in: ["CANCEL_LANGUAGE", "EXPORT_LANGUAGE", "COMPLAINT", "INTENT"] },
    },
    select: { kind: true, payload: true },
    take: 50,
    orderBy: { createdAt: "desc" },
  });
```
Notice: **There is no date filter.** As extractions persist in the database over the lifetime of an account, any customer that lodged a complaint 18 months ago will have that `COMPLAINT` extraction returned in the top 50 rows. In `sensitive.ts:71`, `EXTRACTION_REASON[x.kind]` maps it to `"complaint"`, setting `isSensitive: true` and capping approval level at `DRAFT_FOR_APPROVAL` ("Always human").

### Alternatives & Trade-Off Recommendation
1. **Lifetime Lookback (Current):**
   - *Trade-off:* Eliminates any risk of automated emails reaching historically sensitive accounts, but permanently prevents play automation and auto-send for healthy, recovered accounts, degrading CSM team leverage over time.
2. **Rolling Recency Window (Recommended: 60 Days):**
   - *Trade-off:* Restores automation for accounts where historical complaints have been resolved, while maintaining strict human-in-the-loop protection during active friction. A 60-day window aligns with the text-rule lookback period in the signal engine (`as-of.ts`).
3. **Per-Topic Expiry:**
   - *Trade-off:* Allows fine-grained policies (e.g. `COMPLAINT` expires in 30 days, `CANCEL_LANGUAGE` in 90 days, `LEGAL` lifetime), but introduces configuration complexity and testing surface area for marginal safety gain over a uniform 60-day window.

**Recommendation for Founder Decision:**  
Adopt a **60-day rolling recency window** via `createdAt: { gte: subDays(clock(), 60) }` in `lifecycle.ts:102`. A 60-day window directly mirrors the customer's operational relationship and signal lifetime, preventing permanent automation lockout while ensuring accounts with recent complaints or churn language remain strictly human-supervised.
