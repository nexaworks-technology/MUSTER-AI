### SHOULD-FIX

**S1. The per-model "A cannot update B's row" assertion in the tenant suites cannot fail.**
- *Where:* `src/lib/db/__tests__/tenant-isolation-m3.int.test.ts:180` and the same pattern in the pre-M3 suite `src/lib/db/__tests__/tenant-isolation.int.test.ts:488` (introduced in `ac98182`, M2): `updateMany({ where: { id: bId }, data: {} })` expecting `count` 0.
- *Evidence:* inside a rolled-back transaction on the dev DB, `updateMany({ where: { id: <own row> }, data: {} })` returned **`count: 0` for all 8 M3 models**, on the caller's *own* rows. Prisma updates nothing when `data` is empty, so the assertion passes whether or not isolation holds.
- *Is isolation actually broken?* No. A real attack (non-empty `data`, `_test` DB, rolled back) from `larkspur-demo`'s scoped client gave: SignalRule cross-tenant **0** and own-row **1**; HealthReason cross-tenant **0**. The suite's raw-SQL case also shows RLS hides every M3 table without the workspace setting. The risk is the test's strength, not a leak today.
- *Why fix before M4:* M4 adds new tenant models (AgentRun, Approval, OutboundMessage…) and will likely copy this `CASES` loop, which would spread the blind spot.
- *Fix:* give each case a real field to update, and add a control that the same update on A's own row returns 1. This touches a pre-M3 test file, so it needs the founder's approval under the decision-3 convention. It strengthens the test and loosens nothing.

**S2. Nothing attacks the back-test across workspaces in a way that is guaranteed to run.**
- *Where:* the M3 tenant suite has no back-test case. The only cross-workspace back-test check is `src/modules/health/__tests__/backtest-seed.int.test.ts:91-96`, and it starts with `if (!other) return;`. It passes silently when `ferngrove-test` is not in `_test`. That workspace is created only by other files' seeds (`seed.int.test.ts` with `includeTestTenant: true`, or the e2e global setup), and this file seeds with `includeTestTenant: false`. On a fresh `_test` database the check can pass while asserting nothing. (On this machine Ferngrove exists, so it did assert.)
- *Also untested:* `activateModel`, `previewModelEdit` and `saveModelEdit` given another workspace's model id.
- *Is isolation actually broken?* No. Every back-test function goes through `scopedDb(ctx)`: `backtest-service.ts:62, 161, 251, 267, 328, 381`.
- *Fix:* add back-test cases to the tenant suite with their own two workspaces. Assert that A's `labelledOutcomes` and `buildPoints` never return B's accounts, and that A cannot preview, save or activate B's model id. Replace the silent `return` with a hard requirement.

## 6. Q-44: overall-score cap variants

### Method
- I wrote a temporary TypeScript script in the session scratchpad, **outside the repo**, and ran it with `pnpm exec tsx` against the dev database. It was read-only and is **deleted**; it was never in the working tree.
- It calls the product's own `labelledOutcomes(ctx, "2026-11-02")` and `buildPoints(ctx, outcomes, <SYSTEM_DEFAULT model>)` on `larkspur-demo`, exactly as `backtest-seed.int.test.ts` does. Window 2024-11-01 → 2026-11-02; 12 churns, 12 renewals, 17 weekly points per outcome.
- The cap is applied after the weighted overall: if the lowest non-null pillar is at or below the cap's limit, overall = min(overall, cap value). In V3 the ≤ 15 rule is checked first.
- Catch and false-alarm rules are the same as `evaluateModel`. A churn is caught by its first At Risk point at least 14 days before the outcome. A false alarm is any At Risk point before a renewal.
- **Self-check:** with no cap, my evaluator reproduced the product's `evaluateModel` exactly: default **0/12, 0 FA**; proposal **4/12, mean 28 d, 0 FA**. Both equal `fixtures/backtest-seed.json`.
- Models: **default v1** = weights 30/15/15/20/10/10, Healthy ≥ 70, Watch ≥ 45. **Proposal v3** = 70/5/5/5/5/10, Healthy ≥ 60, Watch ≥ 55.

### Recommendation: reject caps as a model-design rule
1. **They don't fix the problem Q-44 was raised about.** Brightwell and Redfern change band under no variant in either model: their weakest pillars (46, 29) are above every cap limit. Only Pinecrest moves.
2. **Each catch costs a false alarm.**
   - Against the default model, the best variant (V2) gives 4/12 with 1 false alarm. The weight proposal alone already gives 4/12 with 0 false alarms.
   - On top of the proposal, V2 adds one catch (Bluebridge) for one false alarm (Oakcrest).
   - V3 adds a false alarm and no catches in both models.
   - With 12 + 12 outcomes, one account is about 8 points. A +1/+1 trade is not evidence.
3. **A fixed cap is a hand-tuned non-linearity outside the back-test.** It would apply to every workspace, whatever that workspace's own history shows. That contradicts §6C.4: the workspace's own renewed-vs-churned history proposes the model. It also sits uneasily with D-59 (do not tune to a seed target).
4. **Q-44 already has its answer in the shipped mechanism.** On this workspace's history the proposal (v3) catches 4/12 at 0 false alarms and puts Brightwell and Redfern At Risk. The founder's real choice is whether the seeded demo runs with the default or the activated proposal, plus a docs correction to M3.md §6 #4 / §7 step 2 and to SEED_DATA §8's "≈ 8 of 12".

**Proposed DECISION for the founder** (not yet recorded; next free number is D-73):
> *D-73 (proposed): No pillar-floor caps on the overall score.* The overall stays the renormalised weighted mean (D-63). Rationale: on the seed back-test, caps either change nothing (V1), add false alarms without catches (V3), or trade one catch for one false alarm (V2), and they leave the named story accounts unchanged. If floors are revisited, they become a **searched** parameter of the back-test grid (e.g. cap ∈ {none, ≤ 25 → watchMin − 1}), proposed per workspace and shown with its own back-test sentence. They are never a fixed global rule. Q-44 resolution: the seed demo states Brightwell as "Watch under the default model; At Risk under the back-tested proposal", and M3.md / SEED_DATA §8 are corrected to the measured numbers (0/12 default, 4/12 proposal).
