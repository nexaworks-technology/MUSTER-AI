## 1. Goal
Every new customer has an onboarding plan, stalls are flagged with the likely blocker, time-to-value is measured against the account's cohort, there is an adoption view in CS language, and live usage connectors are working.

## 2. In scope
- **Models** ([W], RLS, composite FKs):
  - `OnboardingTemplate` (name, forTier?, forPlan?, steps JSON, `valueDefinition` JSON of measurable criteria);
  - `OnboardingPlan` (accountId, templateId?, startDate, targetValueDate, valueReachedAt?, status `ACTIVE | STALLED | COMPLETE | CANCELLED`, stallReason?, `handoff` JSON with sources per item);
  - `OnboardingStep` (planId, title, ownerSide `US | CUSTOMER`, ownerUserId?, ownerContactId?, dueDate, doneAt?, blockedReason?).
  - `Goal` is created now if not present (Architecture §3.2: accountId, successPlanId?, text, metricKey?, targetValue?, status, sourceType?, sourceId?, quote?, origin, agentRunId?). It is needed for stated goals in the handoff.
- **`src/modules/onboarding/`**:
  - `service.ts`: create plan from template (template chosen by tier/plan), step CRUD, mark done, `valueReached` evaluation.
  - `ttv.ts` (deterministic): days to first value vs the cohort median TTV (cohort = Architecture §4.2 rules). The output is a reason with sources.
  - `stall.ts`: deterministic stall detection and likely-blocker ranking:
    - overdue customer-side step;
    - overdue us-side step;
    - no login/active users in N days;
    - key feature not yet used by day N;
    - TTV beyond cohort P75.
  - `handoff.ts`: Sales handoff assembly. The inputs are:
    - CRM deal/contract fields (from M5 ingest);
    - stated goals (existing `Goal`/`Extraction` rows; call-based goals arrive in M9);
    - key people (StakeholderRole);
    - open risks (Signals);
    - promises made by Sales, which come only if Promise exists (M9). Until then that item says "Promise tracking starts in M9", visible only in the log, not in UI. In the UI the handoff lists only the item types it has.
    Every item has `sources[]`. A missing item says "Not found in CRM" (Rule 4).
  - Jobs: `onboarding.evaluate` runs in the nightly chunk after signals; it runs stall + TTV and updates plan status.
- **Signal rules** (`src/modules/signals/rules/`): `ONBOARDING_STALL`, `ONBOARDING_STEP_OVERDUE_CUSTOMER`, `ONBOARDING_NO_ACTIVITY`, `ONBOARDING_KEY_FEATURE_UNUSED`, `ONBOARDING_TTV_LATE`. Each has the four spec §6D fields and fire / not-fire fixtures.
- **Adoption** (`src/modules/usage/adoption.ts`, deterministic):
  - seats/credits used vs purchased;
  - features used vs bought (FeatureCatalog `includedInPlans`, `isKeyFeature`);
  - power users and their retention;
  - decline curves (28-day vs own baseline).
  Each figure carries sources.
- **Agents** (`src/modules/agents/definitions/`):
  - `onboarding-manager`: tier standard. Trigger: `onboarding.stalled` or a step due. Output: a check-in draft (→ `OutboundMessage` + `Approval`) and an escalation `Task` for the owner/leader. Approval policy: DRAFT_FOR_APPROVAL for all tiers. Prompt: `prompts/onboarding-manager.md`.
  - `adoption-coach`: tier standard. Trigger: adoption signals. Output: the unused-value finding (citing FeatureUsageDaily/FeatureCatalog ids) plus a nudge draft. Default DRAFT_FOR_APPROVAL. Long-tail auto-send is only through plays in M8. Prompt: `prompts/adoption-coach.md`.
  - Both have `forbiddenNumericFields` for any counts/percentages. Numbers come from `adoption.ts`/`ttv.ts` in the context bundle and are re-inserted by code.
- **Usage connectors**:
  - **Usage ingest API** (`POST /api/usage/v1/track`, `POST /api/usage/v1/identify`, `POST /api/usage/v1/batch`):
    - a Segment-compatible subset (`userId`, `groupId`/`accountId`, `event`, `timestamp`, `properties`);
    - authenticated with a per-workspace key that is stored hashed on `Integration` (provider `USAGE_API`), rotatable, shown once;
    - rate-limited;
    - events aggregated into `UsageDaily`, `UserUsageDaily` and `FeatureUsageDaily` by a worker job; raw events are not kept beyond the aggregation window (add to QUESTIONS.md if retention of raw events is wanted).
  - **Segment** destination: the same endpoint, verified with the shared secret.
  - **Mixpanel** and **Amplitude** adapters: export/query APIs → `NormalizedUsageDay` (account + user + feature). Contract tests use recorded fixtures.
- **Screens**:
  - `/onboarding`: every account with an active plan; stage, days in, TTV vs cohort, stall flag and likely blocker, owner; filters by tier and owner; paginated.
  - Account 360 › Onboarding tab: plan steps with owners and dates, handoff panel with sources.
  - Account 360 › Adoption tab (replaces the raw Usage tab framing): CS language ("3 of 5 features in your Growth plan have never been used").
  - Settings › Onboarding templates: CRUD, with value definition builder from known metrics.
  - Settings › Integrations: usage API key management, Mixpanel, Amplitude.

## 5. Tests to write FIRST
- `src/modules/onboarding/__tests__/ttv.test.ts`:
  - value reached on day 18 vs cohort median 21 → "on time";
  - not reached by cohort P75 → late;
  - cohort fallback (fewer than 5 accounts → tier only) is recorded in the reason;
  - no value definition on the template → TTV `null` with "No value definition for this plan", never "late".
- `src/modules/onboarding/__tests__/stall.test.ts`:
  - customer-side step overdue 12 days → stall, blocker "SSO setup (customer) overdue 12 days";
  - us-side overdue ranks above customer-side when both are present (or the reverse; document the chosen order in DECISIONS);
  - no usage data at all → no stall from usage components (Rule 4) and a missing-data note.
- `src/modules/signals/__tests__/fixtures/ONBOARDING_*/*.json`: a fire and a not-fire case for each of the five rules.
- `src/modules/usage/__tests__/adoption.test.ts`: features used vs bought; seats over/under; power-user retention; decline vs own baseline; every figure has ≥ 1 source.
- `src/modules/onboarding/__tests__/handoff.test.ts`: every item has sources; missing CRM fields produce "Not found in CRM" items, not invented ones.
- `src/modules/usage/__tests__/ingest-api.int.test.ts`:
  - a missing or invalid key → 401;
  - **workspace A's key cannot write usage for workspace B's accounts**: a `groupId` unknown in A creates an unmatched record in A only and never touches B;
  - a rotated key invalidates the old one;
  - aggregation is idempotent (re-processing the same batch = same daily totals).
- `src/modules/integrations/adapters/{mixpanel,amplitude}/__tests__/contract.test.ts`.
- `src/modules/agents/__tests__/onboarding-manager.int.test.ts` and `adoption-coach.int.test.ts` (RecordedProvider):
  - the output validates;
  - a citation to an id outside the bundle → `UNCITED` and nothing rendered;
  - a model-supplied count is overwritten by the deterministic value;
  - the draft lands in Approvals (never sent).
