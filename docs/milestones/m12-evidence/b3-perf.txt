== Finding (not fixed: worker code is another session's file) ==
One jobs:nightly re-run on a heavily loaded host (load average ~37) failed: BullMQ "could not renew lock"
on evaluate/score chunk jobs, then "Job wait ... timed out after 600000ms". The same command succeeded on
the next two tries. Cause: CPU starvation delayed the lock-renewal timer (default lockDuration 30 s).
Proposal for src/worker (not touched): set an explicit, larger `lockDuration` (e.g. 120_000) on the
signals and health Workers; attempts:3 already retries the chunk, and the work is idempotent.

== Hotspots ==
None above the 2-minute threshold (largest phase: one 200-account score chunk, 5.7 s quiet).
No query count grows with accounts: every chunk stage uses batch loaders (ARCHITECTURE §11).
No index needed: the heaviest list queries run in tens of ms (table below), so no migration is proposed.
Observation only: renewals list loads ALL in-window renewals (id, ARR, band, category) to compute the
forecast sums (read.service.ts `all`): O(renewals in window) rows per page view; 2,000 rows = 7 queries,
15 ms quiet. Worth moving to a SQL aggregate before ~20k renewals; not needed at 2,000.
Observation: Today = 1 + 2 per section + 1 per non-empty section statements (<= 16), not per item.
Observation: loadChampionGuard (People tab) runs 31 statements, constant in the number of contacts.
