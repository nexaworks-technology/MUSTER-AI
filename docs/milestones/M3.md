## 1. Goal
Ship a deterministic 6-pillar health score where every number opens into proof, CSM Pulse with visible disagreement, a back-tested model proposal, and the nightly (plus single-account real-time) signal engine for structured data.

## 2. In scope
- **Prisma models ([W], RLS, composite FKs, registry):** HealthModel, HealthScoreSnapshot, HealthReason, CsmPulse, UsageBaseline, SignalRule, Signal, OutcomeRecord. DB CHECKs exactly as ARCHITECTURE §3.2:
  - `risk_level <> 'AT_RISK' OR risk_reason_id IS NOT NULL`;
  - `kind = 'MISSING_DATA' OR jsonb_array_length(sources) >= 1`;
  - Signal evidence non-empty;
  - OUTSIDE ⇒ `publicSourceUrl` + `publicSourceDate`;
  - partial unique: one ACTIVE HealthModel per workspace.
- **health engine** (`src/modules/health/engine/`, pure functions, no I/O):
  - **Components** per pillar, per ARCHITECTURE §4.1 (Adoption, Engagement, Support, Relationship incl. CSM Pulse, Commercial, Sentiment).
    - Sentiment components return `null` until extractions exist (M4/M9). The UI shows "Not enough data", never 0.
    - Engagement's meeting component returns `null` until M10 meetings exist.
  - Piecewise-linear curves from `HealthModel.componentConfig`.
  - **Baselines:** own (days −104…−14, ≥ 28 days history) + cohort (tier+plan+employeeBand[+useCase], ≥ 5, stepwise fallback), computed in SQL per chunk into `UsageBaseline`.
  - **Aggregation:** renormalized weights over non-null pillars; < 2 pillars → `INSUFFICIENT_DATA`; thresholds (default 70/45) with per-tier overrides.
  - **Reasons:** deterministic message templates per component (`src/modules/health/engine/reasons.ts`), signed impact, `sources[]`.
  - **Pulse:** component inside Relationship (default 30%), 30-day validity; `overallExcludingPulse`; `pulseDisagreement`.
  - `health.writeSnapshot()` is the only insert path, with a Zod schema requiring reasons per non-null pillar and sources per EVIDENCE reason.
  - `engine.scoreAsOf(accountId, model, date)` uses only records timestamped ≤ date.
  - **Back-test + proposal** (ARCHITECTURE §4.5):
    - weekly as-of over 120 days before each labelled outcome;
    - caught churn ≥ 14 days early, lead time, false alarms;
    - grid search (simplex step 0.05 × thresholds), objective + tie-break as documented;
    - ≥ 5 churned and ≥ 5 renewed, else the default model labelled "default weights — not yet back-tested on your accounts".
- **signals module:**
  - The `SignalRuleDef` registry (`src/modules/signals/rules/`), each rule with `meaning`, `howDetected`, `typicalLeadTime`, `falseAlarmCauses`.
  - Rules in M3, i.e. those M2 data supports:
    - **USAGE:** `usage_drop_vs_normal`, `key_feature_stopped`, `power_user_quiet`, `seats_near_limit` (OPPORTUNITY), `seats_unused` (RISK).
    - **SUPPORT:** `ticket_open_too_long`, `ticket_escalated`.
    - **MONEY:** `payment_failed`, `invoice_late`, `renewal_window_90`, `renewal_window_60`, `renewal_window_30`.
    - **PEOPLE (structured):** `no_meeting_in_x_days`. It returns nothing when the account has no meeting data source yet; the rule never fires on absent data. `contact_bounced_or_left` from Contact.status.
    - **OUTSIDE:** `outside_event` (manual/CSV entries).
  - Seeding inserts one `SignalRule` row per definition per workspace.
  - **Lifecycle:** upsert by `dedupeKey`, resolve when the condition clears, FALSE_ALARM with reason + 30-day cool-off (config).
  - **Outside signals:** manual create form + **outside-signal CSV template** (deferred here from M2); URL + date mandatory; never labelled "new" if the event date is older than 30 days ("Reported 2026-08-14").
- **Pipeline (jobs):**
  - `nightly.kickoff` (repeatable, 02:00 workspace tz);
  - `signals.evaluateChunk` (200 accounts, set-based loads);
  - `health.scoreChunk`;
  - outbox events `signal.opened`, `signal.resolved`, `health.bandChanged`;
  - real-time hook `signals.evaluateAccount(accountId)` called after a CSM Pulse write, an invoice status change and a ticket escalation;
  - dev command `pnpm jobs:nightly --workspace <slug>` (add to CLAUDE.md Commands).
- **OutcomeRecord:** created when a RISK/OPPORTUNITY signal ≥ WARN opens (`arrAtFlagMinor`, `actionTaken = PENDING`). Checkpoints come later.
- **Screens:**
  - `/health`:
    - accounts by band (Healthy / Watch / At Risk / Not enough data);
    - "Moved today" / "Moved this week" with the top reason;
    - "Score and CSM disagree" list;
    - filters by owner/tier/segment; paginated.
  - Account 360 **Health tab:** overall + 6 pillar tiles (null = "Not enough data" grey). Tap a pillar → reason list (message, value, baseline, cohort value, period) → each source pointer links to the record (usage window highlighted on the chart, ticket, invoice, contact).
  - History sparkline from snapshots.
  - Pulse buttons "Actually fine" / "Worried" (+ optional comment) on Account 360 and the Accounts list.
  - Accounts list gains Health + Risk columns, and segments gain health filters.
  - Signals: account Signals tab + `/signals` portfolio list (status, severity, category filters), with "Mark false alarm".
  - `/settings/signals`: each rule with its four spec fields, enable/disable, params (Zod-validated).
  - `/settings/health-model`:
    - active version;
    - proposed draft with the sentence "With this model, we would have flagged X of your last Y churns, on average N days early, with Z false alarms";
    - per-pillar weights;
    - edit → re-run back-test → activate (Admin; CS Leader may propose). Activation is audited and re-scores current snapshots.
- **Seed v2:** run the pipeline in the seed so the demo opens with snapshots + signals for `SEED_TODAY`.

## 5. Tests to write FIRST
- `src/modules/health/__tests__/curves.test.ts`: curve boundaries, monotonicity, clamping.
- `src/modules/health/__tests__/components.test.ts`: per component, a normal case, a null-input case (returns `null`, never 0), and the reason carries sources.
- `src/modules/health/__tests__/aggregate.test.ts`:
  - **missing data never lowers a score** (the same account with an extra null pillar has the same overall);
  - renormalization; < 2 pillars → INSUFFICIENT_DATA;
  - At Risk always has `riskReasonId`;
  - threshold edges 44.99/45/69.99/70; per-tier override.
- `src/modules/health/__tests__/baselines.test.ts`: < 28 days → own baseline null; the 14-day exclusion; cohort fallback order; cohort < 5 handling.
- `src/modules/health/__tests__/pulse.test.ts`: FINE/WORRIED effect inside Relationship; expiry after 30 days; disagreement both directions.
- `src/modules/health/__tests__/write-snapshot.int.test.ts`: Zod rejects a non-null pillar without reasons; the DB rejects AT_RISK without a reason and EVIDENCE without sources.
- `src/modules/health/__tests__/score-as-of.int.test.ts`: records after the as-of date are ignored (usage, tickets, invoices, StakeholderRole validity).
- `src/modules/health/__tests__/backtest.test.ts`: fixture with known churn/renew labels → exact caught/lead/false-alarm counts; proposal deterministic (same input → same weights); insufficient history → default model label.
- `src/modules/signals/__tests__/fixtures/<ruleKey>/*.json` + `rules.test.ts`: every M3 rule has ≥ 1 fire and ≥ 1 not-fire case. The `no_meeting_in_x_days` not-fire case covers "no meeting source connected".
- `src/modules/signals/__tests__/lifecycle.int.test.ts`: re-run → no duplicates; condition cleared → RESOLVED; FALSE_ALARM suppresses the same dedupeKey for the cool-off.
- `src/modules/signals/__tests__/outside.int.test.ts`: missing URL/date rejected (Zod + DB CHECK); old event labelled with its date.
- `src/modules/signals/__tests__/pipeline.int.test.ts`: the nightly run twice yields identical rows; a chunk failure retries without affecting other chunks; query budget per chunk.
- Tenant suite: all 8 new models; plus "workspace A's nightly job cannot read B's usage" (job built with A's ctx, B rows absent).
